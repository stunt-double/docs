AI personas tell you what a careful, unhurried user would hit. Real visitors
tell you what actually happened to them, on their device, on the version you
shipped this morning. The feedback widget closes that gap: one script tag on
your own site, and anyone looking at a page can drop a pin on the exact spot
that confused them and say why.

What arrives is not a support ticket with "the page is broken" in it. It is a
comment attached to the element it is about, with a screenshot of the page as
that person saw it, the URL, the viewport, and which version of the page they
were on.

<Callout variant="who">
  PMs and designers running prototype and staging reviews, founders collecting
  feedback from early customers, and any team tired of screenshots pasted into
  Slack with no idea which page or build they came from.
</Callout>

## Three ways teams use it

The same script tag serves three quite different jobs. What changes is two
settings: **Require sign in** and **Show comments on page**.

<RoleGrid
  items={[
    { role: 'Staging review', gets: 'Require sign in, and the whole team leaves notes in context instead of in Slack.' },
    { role: 'Prototype testing', gets: 'Put a rough build in front of ten early users and watch where the pins cluster.' },
    { role: 'Live product', gets: 'A standing feedback channel on the pages that matter, grouped by page and version.' },
  ]}
/>

**Internal review on staging.** Turn on **Require sign in** and keep comments
shown. Only workspace members can read or leave comments, their notes are
badged **Team**, and a group review becomes one shared thread per issue rather
than five people reporting the same button. It is the cheapest possible
design-review tool: no seats to provision, no file to upload, and the thing
under review is the actual product.

**Prototype and beta testing.** Leave sign-in off and send the link to a
handful of real users. Hide comments on the page if you want independent
reactions rather than people agreeing with the first pin. Where pins cluster is
your friction, and you have the screenshot to prove it. This pairs directly
with persona interviews: run an
[interview](/tutorials/running-an-interview) to find what a careful user hits,
run the widget to find what a hurried one does.

**A standing channel on production.** Leave it installed with sign-in off and
comments hidden from other visitors. People report what bothers them where it
bothers them, and it lands in a queue grouped by page and version rather than
in a support inbox. Declare a version on each release (see
[Versions](/integrations/feedback-widget#versions)) so a week of comments reads
back by build, not by guesswork.

## Close the loop with the people who commented

Collecting feedback and going quiet is worse than not collecting it. The
**Comments** view gives you three ways to answer: reply in the thread (the
reply shows on the page, and the author is emailed if they left an address),
resolve (which notifies the author), and **Summarise**, which turns a busy
queue into themes, open questions and a brief for a coding agent. The
[tutorial](/tutorials/feedback-widget#4-triage-what-comes-back) goes through
each.

The habit that keeps the queue useful: resolve as you ship, and use **Resolve
all** after a round of fixes. An open queue that reflects genuinely outstanding
work gets looked at; one that has become an archive does not.

## Feeding comments back into verification

A comment tells you something is wrong once. A checklist tells you whether it is
still wrong on every deploy. The move that pays off is turning the recurring
ones into checks:

```text
1. Read the open comments for a page (list_feedback, status: "new")
2. Reproduce: run a checklist against that page with the reported flow
3. Fix, then keep the checklist and wire it into a deploy-triggered workflow
4. Resolve the comment (update_feedback_status) so the author is notified
```

The feedback tools are on the MCP server (see
[Use it from an agent](/integrations/feedback-widget#use-it-from-an-agent)), so
an agent can work that loop with you: "read the new comments on the pricing
page, reproduce the top one with a checklist, and tell me what you find." The
`triage_feedback` prompt packages it. See the
**[codebases guide](/guides/codebases)** for the deploy-trigger side, and the
**[validation playbook](/guides/validation)** for turning findings into standing
checks.

## Tips

- Install on staging first, with **Require sign in** on. You get the value
  immediately and nothing is exposed while you are still deciding.
- Only ask for an email if you intend to reply. Collecting addresses and going
  quiet is worse than not collecting them.
- Declare a version if you deploy several times a day. The automatic fingerprint
  works, but grouping by release is unambiguous when you are reading back a
  week later.
- Turn off the `c` shortcut if your own page already uses it. It is one toggle,
  and clashing shortcuts confuse visitors more than they help.
