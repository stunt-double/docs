Figma is where the design decisions happen; Stunt Double is how you find out
whether users can actually follow them. Three pieces cover different moments
in a design's life, and this guide is about which to reach for and how they
combine.

<Callout variant="who">
  Designers validating flows before handoff, design-systems teams guarding
  consistency, and PMs who want usability signal attached to the file, not
  buried in a separate report.
</Callout>

None of them depends on another. Most teams start with the MCP server for
prototype testing, then add the connection once there is a built product to
keep in step with the design. Setup for each lives on its own page:
[MCP](/mcp), the [Figma plugin](/integrations/figma-plugin) and the
[Figma connection](/integrations/figma).

## Test a prototype with personas

Actors drive real browsers, so anything viewable at a URL is testable. For
Figma that means:

- **Prototype share links** (`figma.com/proto/...`) set to "anyone with the
  link can view". Good for click-through flow testing: can a persona find
  their way from the landing frame to the goal?
- **Figma Make published sites** for anything with real interaction. See the
  **[Figma Make guide](/guides/figma-make)**.

From your agent:

> "Use the validate_design prompt on my prototype link with personas for our
> two main segments. Focus on whether the new onboarding order makes sense."

The agent creates an interview, adds task items ("Get from the welcome screen
to creating your first project"), attaches varied personas (mix devices;
prototypes often fail on mobile first), launches, and returns the synthesized
report with transcripts as evidence.

If you also run Figma's own MCP server, the two compose well: Figma MCP reads
and edits the design, Stunt Double MCP tests the result, and the agent carries
the findings from one to the other.

## Review frames before there is a prototype

A prototype link needs wiring. Earlier than that, a static frame can still be
judged. The [Figma plugin](/integrations/figma-plugin) exports the selected
frame for actors to review, places their findings on the canvas as annotations
next to the layers they are about, and re-checks once you have fixed them. It
can also run a project's checklist against a sequence of frames, or hand a
prototype link to Stunt Double to start an interview. Use it for the quick
critique pass inside the file; use an interview when the question is whether
someone can complete a flow.

## Re-check the product when the design changes

This is the predictive half. Once a design has been built, the risk moves from
"can users follow this" to "does the product still match it". With the
[Figma connection](/integrations/figma) in place, an automation can start on a
Figma event:

1. Create checklists for the flows the design feeds, against staging or
   production URLs.
2. Create an automation with the **Figma** trigger on the design file (or the
   library file), and add steps that run those checklists and send a
   notification.
3. Turn it on. The [trigger settings](/integrations/figma#set-it-up) explain
   which events to pick and the access the connected Figma account needs.

intent and the built product surface within minutes of the change, not at the
next QA pass. An agent can set this whole thing up from the `setup_guardrails`
prompt.

## Guard the design system

The same trigger is the natural home for a design-system audit: a reviewer
actor that holds your tokens and component rules, a checklist of visual checks
against staging, and an automation that runs it whenever the library is
published. The **[validation guide](/guides/validation#design-system-adherence)**
covers the pattern, with a complete example, and the `check_design_system` MCP
prompt sets it up.

## Tips

- Keep prototype links public-viewable for the duration of a test; personas
  do not have Figma accounts.
- Name interviews after the design iteration ("Onboarding v3, post-crit") so
  before/after comparisons are easy.
- Re-run the same interview after each iteration rather than starting a new
  one. Unchanged tasks and personas make the differences attributable to the
  design.
- Point the design-change automation at the file that actually changes. An
  automation listens to one file, so a library and the screens built from it
  need one each.
